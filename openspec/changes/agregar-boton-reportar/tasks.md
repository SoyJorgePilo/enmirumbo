# Tareas: agregar-boton-reportar

## Modelo y módulos de dominio

- [ ] 1. Agregar el modelo `Reporte` a `prisma/schema.prisma` (relación con `Negocio` con borrado en cascada, `motivo` texto, `comentario` texto opcional, `estado` texto con default `pendiente`, `creadoEn` con default ahora, `atendidoEn` opcional, índice por negocio + estado) y generar la migración con los CHECK de `motivo` y `estado`. Verificable: una base desde cero migra y corre `npm run db:seed` sin error; `npx prisma migrate status` no reporta drift; el SQL de la migración **crea tabla nueva y no redefine `Negocio`** (los CHECK de `estado` y `origen` del negocio siguen en el esquema, `design.md` §4).
- [ ] 2. Crear `src/lib/reportes/motivos.ts` con la lista cerrada (`cerrado`, `no_real`, `datos_incorrectos`, `inapropiado`), su etiqueta visible ("Ya cerró", "No es real", "Los datos están mal", "Contenido ofensivo o inapropiado"), el tipo del motivo y la función que valida un valor recibido. Verificable: tests unitarios de cada motivo válido, de un motivo inventado, de cadena vacía, de `undefined` y de un arreglo (lo que puede llegar de un `FormData` manipulado).
- [ ] 3. Crear `src/lib/reportes/textos.ts` con todos los literales de la spec (encabezado, frase de la página, rótulos, opciones, ayuda del comentario, botón, confirmación, "Volver a la ficha", errores de motivo, de comentario largo, de guardado y de cupo agotado). Verificable: test que compara cada constante carácter por carácter contra el delta de spec.
- [ ] 4. Crear `src/lib/reportes/limite.ts`: cupo propio de 3 reportes por hora y por IP construido con `crearCupoPorIp` (sin duplicar lógica) y la constante del tope de 10 reportes pendientes por negocio. Verificable: tests de que el cuarto evento de la hora bloquea, de que la ventana se libera al pasar la hora, de que sin encabezado declarado la IP es `null` y no bloquea, y —clave— de que **agotar el cupo de reportes no consume el de altas ni al revés** (`tests/registro-limite-ip.test.ts` sigue en verde).

## Creación del reporte (servidor)

- [ ] 5. Crear `src/lib/reportes/crear.ts` con `crearReporte(prisma, datos)`: recibe el cliente Prisma como parámetro (mismo patrón que `procesarRegistro` y las consultas del panel), valida motivo y comentario (cota de 300, recorte de espacios, comentario vacío → `null`), comprueba que el negocio existe y está `publicado`, aplica honeypot, cupo por IP y tope de pendientes, y devuelve un resultado discriminado (`creado | no-encontrado | error de motivo | error de comentario | cupo-agotado | descartado-silencioso`). Verificable: tests contra la base de prueba para cada rama, comprobando que las ramas bloqueadas **no escriben ninguna fila** y que `descartado-silencioso` (honeypot y tope por negocio) es indistinguible de `creado` para quien envía.
- [ ] 6. Añadir a `src/lib/reportes/crear.ts` (o módulo hermano) las consultas de lectura que necesita el panel: conteo de negocios con reportes pendientes con su total por negocio, y lista de reportes pendientes de un negocio ordenada del más antiguo al más reciente. Verificable: tests con un negocio de tres pendientes + uno atendido (conteo 3, el atendido no aparece), un negocio sin pendientes (no sale en la lista de la cola) y el orden por fecha.

## Superficie pública

- [ ] 7. Crear la página `/negocio/[ficha]/reportar` como Server Component: 404 con `notFound()` si el id no existe o el negocio no está publicado, `h1` "Reportar este negocio", nombre del negocio como texto, la frase de la spec, el grupo de opciones de motivo (ninguna marcada por defecto), el comentario opcional con su ayuda, el campo trampa reutilizando `src/components/registro/campo-honeypot.tsx`, el botón "Enviar reporte", el enlace "Volver a la ficha" y `metadata.robots` con `noindex`. Verificable: la página responde 200 para un negocio publicado con los cuatro motivos y todos los literales en el HTML; responde 404 idéntico para `en_revision`, `rechazado` e id inexistente; no declara `"use client"`.

Verificable: envío válido → pantalla con "¡Gracias por avisarnos! Vamos a revisar este negocio." y "Volver a la ficha"; recargar esa pantalla no crea otro reporte; envío sin motivo → "Dinos qué pasa con este negocio" con el comentario intacto; comentario de 301 caracteres → "El comentario es muy largo (máximo 300 caracteres)"; cuarto envío de la hora → "Ya recibimos varios reportes desde aquí. Espera un rato y vuelve a intentar.".
- [ ] 9. Verificable: el HTML de la ficha trae el literal y el enlace a la ruta de reporte; el botón de WhatsApp sigue siendo el control más prominente; las tarjetas del listado y de resultados no traen ningún control de reportar.
- [ ] 10. Sumar `/negocio/[ficha]/reportar` a las rutas existentes de `tests/layout.test.ts` (revisión de `href` y `action`). Verificable: la suite pasa con el control puesto y falla si el enlace apunta a una ruta inventada.
